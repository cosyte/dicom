Fix the `Dictionary Regen` workflow, red since 2026-06-24 (`DICOM-DICT-REGEN`).

`.github/workflows/dictionary-regen.yml` passed `version: 10` to `pnpm/action-setup@v6` while
`package.json` already declares `packageManager: pnpm@10.0.0`. v6 rejects two sources of truth
outright ("Multiple versions of pnpm specified"), so the job died in roughly 13 seconds at its
first real step, seven runs in a row (four of them pushes to `main`), having never installed
dependencies, never run `pnpm gen:all`, and never compared a generated byte. Dropping the
redundant `version:` input lets `packageManager` win. Same fix `astm` applied to its fuzz
workflow in `44c3d88`.

Two further repairs to the same file, both about the gate asserting rather than merely starting.
The workflow now lists itself in its `paths` filters, so a change to the gate re-runs the gate,
which is what lets the PR fixing a broken gate prove it fixed. And the verify step now fails on
untracked files under `src/dictionary/generated/` as well as modified ones, because `git diff`
sees tracked files only and a newly emitted artifact would otherwise be invisible to it.

The committed dictionary is not drifted. A regen from the pinned `vendor/innolitics/90571bc`
inputs reproduces all four artifacts byte for byte (5,129 tags, 5,035 keywords, 268 UIDs, 617
Annex E entries, zero diff), and that was measured as a positive control: perturbing a VR in the
vendor input reddens the check, restoring it greens it, so the check reads its input. No
regenerated output was committed and no tag-table correction was needed.

CI only. No runtime, public-API, or parse-behavior change.
