**PHI: a sequence the parser could not open was passed through `deidentify()` as raw bytes, so a `(0010,0020)` Patient ID inside it was written into de-identified output next to `(0012,0062) PatientIdentityRemoved = YES`** (`DICOM-DEIDENT-RAWBYTES-PASSTHROUGH`). Pre-existing, live on the published `0.0.6`, and the larger half of the 2,127 leaking grid cells that `#53` decomposed: **1,155 of the 6,348 cells that parse**, every one of them Implicit VR LE and carrying exactly `["DICOM_SQ_NOT_DESCENDED"]`. Re-measured on `scripts/measure-sq-bound-grid.ts` at `d1031f5` before anything was changed, with a negative control (reverting `#53`'s call site restored exactly 2,127, of which 1,250 were Implicit) so the harness is known to be live rather than assumed to be.

When `parseDicom` resolves an element to `SQ` from PS3.6 under Implicit VR LE and the defined-length value turns out not to be a valid `(FFFE,E000)` item stream, it refuses the descent, leaves `Element.items` undefined, keeps the declared span on `Element.rawBytes` and raises `DICOM_SQ_NOT_DESCENDED`. That is the right posture for a parser. It was not a safe one for `deidentify()`, which recurses into a sequence only when its items exist and, for a carrier like `(0008,1115)` that has no Table E.1-1 row of its own, resolved "keep" and re-emitted the span verbatim. The report named nothing.

**The remedy is at the de-identify boundary and reads the parser's own recorded refusal, not the bytes.** PS3.5 2026c §7.5.1 "Item Encoding Rules": "Each Item Value shall contain a DICOM Data Set composed of Data Elements", so an `SQ` value is never legitimately opaque the way an `OB` value is. PS3.15 2026c §E.1.1 "De-identifier": an implementation claiming the Basic Application Level Confidentiality Profile "shall protect or retain all instances of the Attributes listed in [Table E.1-1], whether contained in the top level Data Set or embedded in an Item of a Sequence of Items". A run that cannot enumerate the items cannot discharge that obligation inside them, so it discharges it on the carrier, which is the escalation §E.1.1 makes itself for a SOP Instance UID inside a Sequence ("the enclosing Attribute in the top-level Data Set must be encrypted in its entirety", there stated about the encrypt-and-replace mechanism rather than about Table E.1-1 generally). Both sentences were read from the vendored SHA-pinned documents with the pins re-derived, and each occurs exactly once.

So a **standard** `SQ` element reaching `deidentify()` with no items is now **emptied** to a zero-item sequence, `report.unauditableSequences` records the tag and the byte length dropped, and the new `DICOM_DEIDENT_SEQUENCE_NOT_AUDITABLE` is raised. That record is **capped at `MAX_UNAUDITABLE_SEQUENCE_FINDINGS` (64) across the run** - element count is attacker-chosen exactly as a value's length is, and `#48` bound every other consumer-controlled diagnostic - while the **emptying itself is never capped**, so an array exactly 64 long means "at least 64". A listed sequence an active Retain Option keeps takes the same branch, and its audit line now says `emptied` rather than `kept`: previously `descendSequence` rebuilt it from `el.items ?? []` and produced an empty sequence anyway, while the report claimed the attribute was retained.

**This costs content, and the number is published rather than described.** On the grid, 2,448 cells lose a value from their de-identified output: 1,155 where those bytes were leaking a source identifier, and **1,293 where they were not** and the drop buys only the guarantee. That is the fail-safe direction and it is a real trade, not a free win. The `DICOM_SQ_NOT_DESCENDED` warning on `ds.warnings` says why the parse refused, which is _usually_ a sender-side encoding defect - but not always, and the artifacts must not say otherwise: a **conformant** file nested deeper than this library's own `NESTING_DEPTH_LIMIT` of 64 (ours, not PS3.5's, which sets no nesting bound) is refused the same way and loses that sequence too.

**Because the trigger is `items === undefined` and not a content test, there is no scan and no cost that follows an attacker-chosen value length** - the failure mode `#53` shipped for one round, where re-scanning a tail once per candidate offset turned 256 KiB into 22.5 s inside `deidentify()`. The cost tests here use a carrier filled with `FE FF`, so **every even offset** is a tiling candidate, and that property is asserted rather than described (`#53`'s cost test was green because its fixture produced exactly one candidate). Be precise about what they are, though: this path never traverses those bytes, so they are a **forward tripwire** against a content test being added here, not a measurement of a loop that exists.

**New public surface:** `UnauditableSequenceFinding`, `DeidentifyReport.unauditableSequences`, and the `DICOM_DEIDENT_SEQUENCE_NOT_AUDITABLE` warning code (**27 Tier-2 codes, was 26**; the locked snapshot was updated deliberately). `DICOM_SQ_NOT_DESCENDED`'s message text changed, because it said nested content was invisible to de-identification, which is no longer what happens.

**What is NOT covered, and one of the two is now measured for the first time.** An undefined-length **`UN`** whose CP-246 descent was refused keeps `vr === "UN"`, so this rule does not reach it, and it cannot be extended there: every ordinary `UN` element also has no items, so the same test would empty every unknown-VR element in every file. Measured on a hand-built file: the identifier still reaches de-identified output, with no report entry. A **private** `SQ` retained under `RetainSafePrivate` plus a `Profile` is still kept verbatim, unchanged and deliberate, because the profile has vouched for it by creator and tag - `keepsPrivate` decides before this rule is consulted, so such an element never reaches it, and measured on a synthetic vendor block the identifier does still reach output. Pinned by a test so the carve-out and the claims cannot drift apart. And the **binary-VR carrier residual** `#53` disclosed but could not measure now has a number: the grid gained an over-declaring **leaf** carrier dimension, which finds **19 leaking cells, identical on both trees** and split across two mechanisms - 11 at `delta=18` (the over-declare swallow into `OB`/`OW`/`US`/`UN`, silent, with the `LO`/`ST` controls on the identical fixture at 0) and 8 at `delta=-6` (an _under_-declare, where the leftover bytes are read as a Data Element header and the identifier lands inside a manufactured element with an unknown on-wire VR; this one hits string carriers too and was not disclosed anywhere before).

**Re-derivable, on the now 76,599-cell grid against `d1031f5`:** sequence-sweep leaks 1,155 → **0**; **0 cells differing in any parse respect**, now a printed count rather than an inference from `changed`, because no parser file is touched; 0 new fatals, 0 lost parse values, 0 reports that lose an attribute, 0 new strict fatals.
