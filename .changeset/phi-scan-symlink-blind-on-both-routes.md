**A symbolic link under `test/fixtures/` pointing at a file full of PHI passed the repository's PHI commit gate on both of the routes that gate has.** The scanner now refuses to report a scan clean when it has reached an entry it cannot account for.

**Reproduced before anything changed.** A synthetic, name-bearing payload was written outside the walk root and a link to it placed at `test/fixtures/leak.txt`: the all-files sweep exited 0 printing "OK - no hits", the staged sweep exited 0 after `git add`, and naming the target file directly exited 1 with three hits. The payload was always detectable. Neither route ever looked at it.

**Two mechanisms.** The directory walk enumerates entries that answer "is a regular file", which is an lstat answer, so a link is neither a file nor a directory and fell out of the loop in silence. That is also true of a link to a **directory**, so a whole subtree could vanish the same way (measured). The staged route reads content with `git show :<path>`, and git stores a symbolic link as its **target path** under mode 120000, so it was handed the path text rather than the target's bytes. The staged route is this repository's pre-commit hook.

**Neither route is made to follow the link, and that is the design rather than a shortcut.** Following one would read bytes the enumeration does not control: outside the repository, a loop, a device, or a FIFO that blocks the gate forever. Git does not carry those bytes in any case, so a hit on them would be a claim about something no commit contains. The enumeration is narrowed instead. An in-scope entry that is not a regular file **refuses the scan** and exits 2, naming every offender rather than the first, because a developer who has to re-run a gate once per link learns to distrust it.

**The staged route needed one more letter than it looked.** It now reads the raw form of the staged diff so the destination mode is visible, and refuses a symbolic link and a nested repository. Its status filter admits **typechange** as well as add and modify: replacing an already-tracked file with a link is neither an add nor a modify, and measured on git 2.39.5 the add-and-modify filter prints nothing at all for that stage. Without typechange the mode check was unreachable for any file already in the repository, and the hook would have passed a mode-120000 blob green while this note claimed it refuses one. Typechange carries a single path, exactly like add and modify, so admitting it costs the record parsing nothing, and the reverse case (a link replaced by a real file) is now scanned as the file it became. A staged-diff record the parser cannot read refuses too, rather than being skipped: a silently shortened list is the one thing this scan must never report clean over.

**A refusal names the entry's own repository-relative path and a fixed token for its kind. It never reports the link target.** A target path is working-tree text and can itself carry PHI, and that is not hypothetical: on the previous scanner, a link whose target filename carried a name and a date made the staged route exit 1 and print a hit whose value was the date **out of the filename**, a report about the working tree's own text rather than about anything the target contained. For the same reason the scanner's own documentation writes out the shape of such a filename instead of giving an example. A diagnostic about a PHI leak is itself a PHI surface, and that applies to the prose explaining it.

**Scope is narrowed, never widened.** The sweep still walks only the fixture root and still excludes a gitignored entry, by the same rule that already excludes a gitignored fixture, so links do not get a second and stricter boundary of their own. The staged route still looks only at the fixture prefix. A link outside either boundary is left alone, and both directions are pinned by tests so the claim cannot drift from the code. The exemption that skips a `README.md` deliberately does not reach a link: that exemption is a judgement about a file whose bytes the walk could have read, and a link's name is no evidence about what is on the other side of it.

**What pins it.** The scanner's test suite gained cases on both routes, each running against a throwaway repository rather than this one, with a synthetic name-bearing payload whose target filename also carries a name, so the assertions that no PHI reaches a refusal cannot pass by fixture. **10 of the 28 cases are red on the previous commit.** The suite also carries a negative control asserting that the scanner under test belongs to this package and not a sibling.

**Not closed here, each measured rather than assumed.** Naming a path explicitly on the command line already read through a link and is unchanged. Staged renames and copies are still not enumerated by the staged route at all, so a staged rename that appends PHI passes it; admitting them needs a two-path record shape handled, which is a scope decision rather than this one, and if such a record ever reached the parser it refuses. A file that vanishes between being enumerated and being read still aborts the whole sweep, which fails closed and is a different defect. There is still no rule refusing a scan that observed nothing at all, and the bypass flag with no path alongside it still scans nothing and prints "OK - no hits" even for a path that does not exist, which makes one existing test in this suite vacuous. All pre-existing, disclosed rather than fixed.

No source, parser, de-identify or public API change.
