The DICOM JSON converters follow PS3.18 Annex F (2026d) where they did not: key order, `DS` and `IS` strings, and `BulkDataURI`.

- **Attribute order (PS3.18 F.2.2).** The annex orders a Data Set's attributes by tag, ascending. `toDicomJson` now adds them in that order at every depth, whatever order the file held them in. A JavaScript object still lists an all-digit tag such as `60000010` (Overlay Rows) first, so `JSON.stringify` cannot keep the order. New export: `stringifyDicomJson(json, space?)` writes the JSON text with every Data Set's attributes in ascending order, and otherwise the same text as `JSON.stringify`. To write annex-ordered text, call `stringifyDicomJson(json)` where you called `JSON.stringify(json)`; nothing else changes for a caller. The docs no longer say the keys come in Data Set order.
- **`DS` and `IS` as JSON strings (PS3.18 F.2.3).** `fromDicomJson` now reads a `DS` or `IS` value given as a JSON string, which the annex allows beside a number, and writes it as its own text, so `"1.50"` stays `1.50`. A string that is not a `DS` or `IS`, or is longer than the 16 or 12 bytes PS3.5 allows, is refused with `MALFORMED_VALUE`; an `IS` string out of range with `UNREPRESENTABLE_NUMBER`. These were refused with `INVALID_JSON` before.
- **`BulkDataURI` on every VR the annex names (PS3.18 F.2.2).** `fromDicomJson` now takes a `BulkDataURI` on `DS`, `FL`, `FD`, `IS`, `LT`, `SL`, `SS`, `ST`, `SV`, `UC`, `UL`, `US`, `UT` and `UV` as well as the seven binary VRs, and hands the URI and the VR to `resolveBulkData` as before. A `BulkDataURI` on another VR, or beside a `Value`, is still `INVALID_JSON`, and `InlineBinary` stays with the binary VRs. On the fourteen VRs newly taken, where any `BulkDataURI` was `INVALID_JSON`, one the resolver does not resolve is now `BULK_DATA_UNRESOLVED`, one it throws for is `CONVERSION_FAILED`, and bytes for a VR of numbers that are not a whole number of values are `MALFORMED_VALUE`.
- **Bulk data under Big Endian (PS3.18 8.7.3.3.1).** A DICOMweb service serves uncompressed bulk data in Little Endian, so under Explicit VR Big Endian `fromDicomJson` now swaps the bytes `resolveBulkData` returns, value by value, for `OW`, `OF`, `OD`, `OL`, `OV` and the number VRs, rather than refusing them with `UNSUPPORTED_BYTE_ORDER`. `resolveBulkData` should return Little Endian bytes. Each `BulkDataURI` on `OW`, `OF`, `OD`, `OL` or `OV` under Big Endian was `UNSUPPORTED_BYTE_ORDER` before; now fetched bytes that are not a whole number of values give `MALFORMED_VALUE`, a URI that is not a string `INVALID_JSON`, one the resolver does not resolve `BULK_DATA_UNRESOLVED`, and one it throws for `CONVERSION_FAILED`.
- **`InlineBinary` under Big Endian is still refused.** PS3.18 F.2.7 defers the `InlineBinary` form to PS3.19 Table A.1.5-2, which names no byte order, so an `OW`, `OF`, `OD`, `OL` or `OV` `InlineBinary` under Explicit VR Big Endian stays `UNSUPPORTED_BYTE_ORDER`, and the docs and the error message now say why.
- **Encapsulated Pixel Data by URI.** The annex has no inline form for a fragment stream, so `toDicomJson` now asks the `bulkDataUri` option for encapsulated Pixel Data and writes the `BulkDataURI` it returns. With no URI it is still refused with `UNSUPPORTED_ELEMENT`, `inlineBulkData` or not.

Round trips of JSON the converters read before are unchanged.
