**PHI: an element that over-declared its own Value Length swallowed the next element into its value, and `deidentify()` wrote the identifier straight into its output with a clean report** (`DICOM-OVERDECLARE-SWALLOWS-INTO-VALUE`). Pre-existing, live on the published `0.0.6`, and **no sequence is involved** - every prior fix in this family was about a sequence's or an item's extent; this is a layer beneath them.

PS3.5 2026c defines Value Length as "The length of the Value Field of the Data Element". A sender that writes a larger number does not produce a detectably broken file: the reader consumes the declared count, the bytes it over-consumes are the following element header and all, and every subsequent offset still lines up. After the swallow there is no `(0010,0020)` in the object for PS3.15 Table E.1-1 to match - only bytes inside some other attribute's value - so de-identification passed over an identifier it never recognised as an attribute. Measured on `scripts/measure-sq-bound-grid.ts` at `244a372`: **877 of the 6,348 cells that parse** wrote a source value into de-identified output this way, **871 of them silently** (no warning on either channel, no throw under `{ strict: true }`).

**`parseDicom` is unchanged, and that is the design.** An over-declaring element and a well-formed one that simply has an odd value produce identical bytes; intent is not on the wire, so a parser cannot choose between the two readings and this release does not pretend to. The remedy sits at the de-identify boundary, where the obligation actually is: PS3.15 §E.1 requires a de-identifier to "protect or retain all instances of the Attributes listed in [Table E.1-1]", and §E.3.5 is the standard's own statement that identifying information embedded **inside a string attribute's value** is in scope for removal.

Before keeping a value, `deidentify()` now asks whether the value's tail decodes - in the file's own transfer syntax - as a complete run of Data Elements ending **exactly** at the end of the value, at least one of which **this run** would have acted on (the same `resolveAction` the Basic Profile and every active Retain Option resolve through, so `RetainUIDs` narrows it exactly as it narrows the action table), and containing a byte the carrier's VR **cannot legally hold** (PS3.5 §6.1.2.1). All three conjuncts must hold. If they do, the value is **emptied** rather than kept, `DICOM_DEIDENT_EMBEDDED_ATTRIBUTE_REMOVED` is raised on `report.warnings`, and the new `report.embeddedAttributes` names the carrier, its VR, the tags that were hiding inside it and the sequence context path.

**New public surface:** `EmbeddedAttributeFinding`, `DeidentifyReport.embeddedAttributes`, and the `DICOM_DEIDENT_EMBEDDED_ATTRIBUTE_REMOVED` warning code (26 Tier-2 codes, was 25).

**What is NOT covered, stated because a guarantee believed to be wider than it is would be worse than none.** Carriers are **string VRs only**: a swallow into `OB`, `OW`, `UN` or another binary VR is indistinguishable by content from legitimate data, and scanning those would trade a measured guarantee for a coin-flip that deletes real pixel and lookup-table content. A sequence the parser declined to descend and kept as opaque bytes is a different defect, untouched here (1,155 grid cells, all Implicit VR LE, all carrying `DICOM_SQ_NOT_DESCENDED`). And nothing here recovers the correct reading: the carrier's parsed value still holds the absorbed bytes and `ds.get("00100020")` still returns nothing. This closes the leak, not the mis-read.

**Re-derivable, on the committed 76,293-cell grid against `244a372`:** 2,127 leaking cells → 1,155, every Explicit VR cell → **0**, and **0 cells whose parse differs in any respect** - reading, both warning channels, `{ strict: true }` and which values survive anywhere in the object are byte-identical, because no parser file is touched. 0 new fatals, 0 lost values, 0 reports that lose an attribute. `scripts/measure-sq-bound-grid.ts` previously existed only on an unmerged branch; it is committed here so "re-run the grid" is an instruction someone can follow.
