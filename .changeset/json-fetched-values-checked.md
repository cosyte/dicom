`fromDicomJson` checks text fetched through `BulkDataURI` as it checks the same text given inline, and `toDicomJson` writes a `DS` no JSON number holds as a string.

- **Fetched text is checked (PS3.18 F.2.2).** Bytes `resolveBulkData` returns for a `DS`, `IS`, `LT`, `ST`, `UC` or `UT` were written as they came, so `abc` fetched for a `DS`, or an `LT` holding ESC, was accepted where the same value given as a `Value` was refused. Each fetched value is now held to the checks of its VR and refused with the code inline text gets: a `DS` or `IS` that is not one, or is longer than its 16 or 12 bytes, and a control character the VR does not allow, `MALFORMED_VALUE`; an `IS` out of range, `UNREPRESENTABLE_NUMBER`; bytes the Specific Character Set does not define, such as a byte past `0x7F` under the default repertoire or a C1 byte under `ISO_IR 100`, `UNSUPPORTED_CHARACTER_SET`; and bytes that are not UTF-8 under `ISO_IR 192`, `MALFORMED_VALUE`. Each of these was accepted before. A caller whose resolver returns such bytes now gets the refusal; send the value inline to see the same code.
- **A `DS` no JSON number holds exactly is a JSON string (PS3.18 F.2.3).** `toDicomJson` refused a `DS` such as `9007199254740993` or `1e400` with `UNREPRESENTABLE_NUMBER`. It now writes the text, its leading and trailing padding spaces dropped, as a JSON string, which the annex allows and `fromDicomJson` writes back as the same text. The string is written only where it is a `DS` of at most the 16 bytes PS3.5 allows, which is all `fromDicomJson` reads, so a longer one such as `0.10000000000000001` is still `UNREPRESENTABLE_NUMBER`. A caller that reads the `Value` of a `DS` should expect a string beside numbers. A `DS` that is not a number, and an `IS` no double holds (longer than the 12 bytes PS3.5 allows), are still `UNREPRESENTABLE_NUMBER`.
- **`stringifyDicomJson` orders tags by value and calls `toJSON`.** A tag with lowercase hex letters sorted after every uppercase one, so `0010000a` came after `0010000B`; tags now sort by value, whatever the case. A `toJSON` method on a Data Set, an attribute or a Sequence's Items was not called, while one on a value was; each is now called as `JSON.stringify` calls it, once, with its key. An error a `toJSON` throws, or a Data Set whose `toJSON` gives no text, is `CONVERSION_FAILED`.
- **`SV` and `UV` stay refused, and the message says why.** A JSON number holds an integer exactly only up to 2^53, and these VRs hold integers up to 2^63 and 2^64, so a `Value` of either is still `UNSUPPORTED_VR` until we have read the form the annex gives them in a pinned copy of PS3.18. The `UNSUPPORTED_VR`, `UNREPRESENTABLE_NUMBER` and `MALFORMED_VALUE` messages are reworded to match; the codes are the same.
