**PHI: an element whose on-wire VR is not one of the 34 PS3.5 §6.2 defines was kept verbatim by `deidentify()`, carrying a source `(0010,0020)` Patient ID into de-identified output next to `(0012,0062) PatientIdentityRemoved = YES`** (`DICOM-CARRIER-LEAF-LEAKS`, mechanism 2). Pre-existing, live on the published `0.0.6`, and identical on both trees. Re-derived on `scripts/measure-sq-bound-grid.ts` at `35adc2d` before anything was changed: **19 leaking cells → 11**, with a negative control first (running the grid against `d1031f5`'s `src/` restored **1,174** leaking cells and reproduced `#54`'s published cost of 2,448, so the harness is known live rather than assumed) and a second control confirming the harness fails outright when pointed at another package.

**This is the _under_-declare, and it is not the swallow `#53` closed.** An over-declared Value Length absorbs the following element into this one's value. An **under**-declared one desynchronizes the reader instead: it finishes the short value early, reads the leftover bytes of the value that was actually encoded as the next Data Element header, and consumes the element that genuinely followed as that fabricated element's "value". Tag, VR and length are then all fragments of somebody's value. Measured: a 14-byte carrier under-declaring by 6 yields tag `(4156,554C)` with the VR bytes `"E "` and a length of 16, holding the Patient ID in full, **silently** and with a clean report - `ds.warnings` is empty and `{ strict: true }` does not throw. **It reaches string carriers exactly as it reaches binary ones** (6 of the 8 leaking cells were Explicit VR LE, two of those the `LO` and `ST` controls), so it is not bounded by the binary-VR story that frames the sibling mechanism.

**The remedy is at the de-identify boundary and reads a field the parser already recorded, not the bytes.** PS3.5 2026c §6.2 "Value Representation (VR)": "All new VRs defined in future versions of DICOM shall be of the same Data Element Structure as defined in [§7.1.2] with reserved bytes after the VR and a 32-bit unsigned integer VL (i.e., following the format for VRs such as OB or UT)". An unrecognized VR is therefore long-form by the standard's own structure rule, while this parser reads it **short-form** - it trusts the two on-wire bytes (Postel's Law) and only `LONG_FORM_VRS` takes the long layout. So its length field was read from the wrong two bytes and its "value" spans the wrong bytes; those bytes are not a Value Field this library decoded under any VR, and PS3.15 2026c §E.1.1's obligation to "protect or retain all instances of the Attributes listed in [Table E.1-1]" cannot be discharged inside them. Both sentences read from the vendored SHA-pinned documents with the pins re-derived (`part05` `4dfd7b8c…`), and each occurs exactly once in its document. Note what §6.2's **note** says next to that, because it cuts the other way and the slice does not rest on it: informatively, "an implementation may choose to ignore VRs not recognized by applying the rules stated in [§7.1.2]", and an unrecognized-VR element's value "may be copied unchanged". The standard therefore treats such an element as a real Data Element with a real Value, read **long-form**. **This parser does not** - it reads an unrecognized VR short-form, so a §6.2-conformant future-VR element (long form, reserved bytes, 32-bit VL) is a fatal parse here on both trees. That is the root cause of this defect class, it is `PRE-EXISTING` and unchanged by this slice, and emptying at the de-identify boundary is compensation rather than conformance. Filed for its own slice; the "shall" quoted above is normative and is what this rests on.

Such an element is therefore **emptied**, `report.undefinedVrElements` records the **byte offset** and the byte length dropped, and the new `DICOM_DEIDENT_UNDEFINED_VR_NOT_AUDITABLE` is raised. **The test is a set-membership check on `el.vr`** - O(1), no scan, no per-offset loop, and no cost that follows an attacker-chosen value length, which is the quadratic surface `#53` shipped for one round.

**The diagnostic names no tag, uniquely among this report's findings, and that is the point.** The condition that raises it is that the element's header was fabricated out of the middle of some element's Value Field - so its four tag bytes and its two VR bytes are document content, not structural fields. On a synthetic `ST` carrier holding `"MR BRAIN SMITHSON"` the fabricated tag renders as `48544F53`: four letters of the surname. `renderTag` validates a tag's _shape_ and so cannot refuse one, unlike its `renderVr` sibling, which makes this the one factory where the "structural by construction" property of `WarningTokens` has to be kept by not passing the field at all. The byte offset identifies the element instead. The first draft of this slice did emit that tag, on both channels, under an explicit "safe to log" claim - and its test could not catch it, because the fixture's carrier value was the benign `"CARRIER-VALUE"` whose leftover bytes are `"VALU"`. The tests now run on a name-bearing payload, and re-adding the tag turns three of them red.

**No carve-out, and the reason is structural rather than a promise.** `keepOrEmpty` is the only path in the module that writes a source value into de-identified output unchanged, and the test sits at the top of it; every other outcome (`X` remove, `Z`/`C` empty, `D` dummy, `U` remap, private-by-default removal) has already replaced the value. So an element a `Profile` vouches for under `RetainSafePrivate` is still emptied - pinned by a test, because the sibling `SQ` rule's equivalent claim was false in exactly that spot and `#54` was refuted for it.

**The record is capped at `MAX_UNDEFINED_VR_FINDINGS` (64) across the run; the emptying never is.** The amplification is worse than the sibling's, not better: an undefined-VR element is read short-form, so the cheapest one an input can encode is an **8-byte header with a zero-length value**, and a 1 MiB file is 131,072 of them. The cap is on `DeidentifyContext` rather than a `ProcessResult` because `processElements` builds a fresh result per Data Set and merges upward, so a per-result cap would bound each sequence item and not the file. The warning text omits the tag and the VR deliberately - see above; both are input, emitted once per element.

**`UN` is untouched, and that line is the point.** `UN` is one of the 34, so this never fires on an ordinary unknown-VR element: not the Implicit VR fallback for an unpublished tag, not a private element with no reachable creator, and not the CP-246 `UN` whose descent was refused. Under **Implicit VR LE it cannot fire at all**, because the VR is resolved from the dictionary - which is why 0 Implicit VR LE cells moved. Widening this to "unknown to the dictionary" would empty every `UN` element in every file; that residual still needs a parser-set mark and its own slice.

**What it costs, published rather than described:** 23 grid cells lose a marker from de-identified output, **15 of which were not leaking anything** and pay only for the guarantee. On a file conformant to PS3.5 2026c the cost is zero - a sender that writes one of the 34 VRs that edition defines never produces one, and an Implicit VR LE file cannot.

**One report-channel move, which no other artifact would have told you:** an undefined-VR carrier whose bytes happened to tile as Data Elements was reported in `report.embeddedAttributes` (with the embedded tag list) before; it now reports in `report.undefinedVrElements` instead. Same emptying, different array.

**New public surface:** `UndefinedVrFinding`, `DeidentifyReport.undefinedVrElements`, and the `DICOM_DEIDENT_UNDEFINED_VR_NOT_AUDITABLE` warning code (**28 Tier-2 codes, was 27**; the locked snapshot was updated deliberately). `isScannableCarrier` in `src/deident/embedded.ts` lost its "VR not one of the 34" disjunct: the new rule empties such an element before the scan is reached, so the branch was unreachable - and conditioning the answer on a tiling run was the defect, since an undefined-VR element whose bytes did not happen to tile was kept.

**Still leaking, measured, and now priced - it is a product decision, not a bug fix.** The 11 remaining cells are mechanism 1: the over-declare swallow into a **binary** carrier (`OB`/`OW`/`US`/`UN`) at `delta=18`, silent, with the `LO`/`ST` controls on the identical fixture at 0. No content test can decide it, because arbitrary bytes are exactly what those VRs are for. The one candidate remedy - drop the repertoire conjunct for binary VRs and scan on the other two - was **built and measured**: it takes those 11 to 0, and it empties **all 5** of the grid's new conformant tiling controls, i.e. a de-identifier deleting a legal `OB`/`UN` value because 8 of its bytes happened to read as a zero-length `(0010,0020)`. `scripts/measure-sq-bound-grid.ts` gained that control family (`LEGIT_TILING_CARRIERS`, stride-0 VRs only so the Big Endian value swap cannot make a row mean something it does not) and prints `conformant tiling control emptied` for both trees, so the trade is a number.

**Re-derivable, on the now 76,611-cell grid against `35adc2d`:** leaking 19 → **11**; **0 cells differing in any parse respect**; 0 Implicit VR LE cells changed at all; 0 new lenient fatals, 0 new strict fatals, 0 lost parse values, 0 PHI regressions, 0 reports that lose an attribute.
