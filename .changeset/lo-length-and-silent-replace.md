🩺 `(0012,0063)` De-identification Method: the text this library writes for itself is now inside the 64-character maximum PS3.5 gives an `LO` **Value**, and the one replacement that was still silent now reports.

`PRE-EXISTING` and measured through the built package on `da1f209`: the default method was a single Value of **76** characters, **130** with `RetainUIDs + RetainSafePrivate + RetainDeviceIdentity` and **272** with all nine, so **all 512 option subsets** were over the maximum, on every object de-identified without a caller-supplied method. PS3.5 2026c Table 6.2-1's `LO` row is "64 chars maximum" and describes a **Value**; `(0012,0063)` is `1-n`, so the bound is per value. The default is now multi-valued: one Value naming the Profile (**61** characters) and one per active Option (**28** at most). Swept over all 512 subsets / 2,816 value cells: **0** over the maximum, against **512 of 512** before. Options are emitted in `DEIDENTIFY_OPTIONS` order, so the same set always writes the same bytes, and the fixed point is re-measured over six wire round trips at a flat **62** bytes by default and **248** with all nine.

**The method text changes**, so a consumer that string-matches `(0012,0063)` against the old value will stop matching. `Cosyte` and `PS3.15` came out of it because they were redundant with `@cosyte/dicom` and with the profile's own name, which is quoted from that part.

New Tier-2 code **`DICOM_DEIDENT_METHOD_NOT_LO`**: a `(0012,0063)` a file encoded under any other VR is still **replaced** (the join concatenates `LO` values with `5CH`, which is not defined over arbitrary octets, and guessing an encoding was refused), but that replacement is no longer silent. It is separate from `DICOM_DEIDENT_METHOD_NOT_ADDED` because the causes are unrelated. An empty or padding-only prior raises neither. The message carries no value, no length and no VR.

**Two costs, disclosed rather than fixed.** A `deidentificationMethod` of your own longer than 64 characters, and a prior value the source file wrote longer than it, are both written through undisclosed: splitting or truncating either would invent a record nobody made. **The most likely writer of an over-long prior value is this library** - every object `0.0.3` through `0.0.11` de-identified without a caller-supplied method carries the 76-character one, and re-de-identifying such an object keeps it (a flat 138 bytes over four passes, values of 76 and 61, with `DICOM_DEIDENT_METHOD_PRIOR_RETAINED` raised for the retention and nothing said about the length). Keeping it is still correct, because "added to" is what PS3.15 E.1.1 says and rewriting a prior record destroys provenance whoever wrote it. Both costs are pinned as residual tests. And `{ strict: true }` still renders 16 raw source bytes in `DicomParseError.snippet` at the warning's own offset, which is the documented design of that field. **The two duplicate codes place that offset differently, and a graded pass refuted the draft that said they agree**: `DICOM_DUPLICATE_FILE_META_ELEMENT` points at the **dropped** element (`AE-SMITHSON` comes back as `41 45 2d 53 4d 49 54 48`, the value its message withholds), `DICOM_DUPLICATE_TAG_IN_DATA_SET` at the **surviving** one (`53 55 52 56 49 56 4f 52`). The over-broad claim that "the diagnostic is not itself a PHI surface" was corrected and both paths pinned byte for byte, since redacting `snippet` is a decision about every Tier-3 fatal in the library.
